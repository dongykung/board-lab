## 이 문서의 성격

지금 당장 구현하는 문서가 아니라, **나중에 "강제 로그아웃"이나 "중복 로그인 제한"이 실제로 필요해졌을 때** 참고할 전환 계획서입니다. `SessionAuthStudy.md` / `LoginFeatureGuide.md`로 구현한 현재 방식(Cookie Authentication, self-contained)의 한계와, 서버 세션으로 넘어갈 때 무엇이 바뀌는지를 미리 정리해둡니다.

<br>

## 왜 필요해지는가 (전환 트리거)

현재 방식(쿠키 안에 `ClaimsPrincipal`을 암호화해서 통째로 담는 방식)은 서버에 "지금 유효한 쿠키 목록"이 전혀 없습니다. 그래서 아래 세 가지가 구조적으로 불가능합니다.

| 하고 싶은 것 | 왜 지금 방식으론 안 되는가 |
|---|---|
| 관리자가 특정 유저를 지금 즉시 로그아웃 시키기 | 서버가 그 유저의 쿠키가 어디 있는지, 몇 개인지 전혀 모름 |
| "다른 기기에서 로그인하면 기존 로그인은 끊기" (중복 로그인 제한) | "이 계정으로 지금 활성 세션이 몇 개인지" 셀 저장소 자체가 없음 |
| "현재 로그인된 기기 목록" 같은 조회/감사 기능 | 마찬가지로 활성 세션 저장소가 없음 |

이 중 하나라도 실제 요구사항이 되는 시점이 전환 시점입니다. (성능/확장성 문제로 전환하는 게 아님 — 오히려 지금 방식이 무상태라 서버 확장에는 더 유리함. `SessionAuthStudy.md` 트레이드오프 표 참고)

<br>

## 핵심 아이디어

쿠키 안에 **사용자 정보(Claims) 자체**를 넣는 대신, 쿠키에는 **의미 없는 랜덤 세션 ID**만 넣습니다. 진짜 사용자 정보와 "이 세션이 아직 유효한가"는 서버 저장소(DB 테이블)가 갖고 있고, 매 요청마다 그 ID로 조회해서 판단합니다.

```
[현재 방식]  Cookie = 암호화(UserId, LoginId, 만료시각, ...) 전부 포함
[전환 후]    Cookie = 랜덤 세션ID 하나만 포함
             서버 DB: SessionId -> { UserId, 만료시각, 무효화여부, ... }
```

<br>

## 구현 경로 두 가지

### 경로 A. ASP.NET Core `ITicketStore`를 Cookie Authentication에 꽂기 (권장)
- `AddCookie(options => options.SessionStore = new MyTicketStore(...))` 처럼 기존 `AddCookie` 설정에 저장소만 하나 추가
- `SignInAsync` / `SignOutAsync` / `[Authorize]` / `HttpContext.User` — 지금 쓰던 API가 전부 그대로 유지됨
- 내부적으로만 "쿠키에 Claims 통째로" → "쿠키엔 키만, 값은 `ITicketStore` 구현체(DB)에 저장"으로 바뀜
- **마이그레이션 비용이 가장 적은 방법** — Controller/Service 코드는 손댈 필요 없음

### 경로 B. Cookie Authentication을 걷어내고 직접 구현
- 커스텀 미들웨어에서 쿠키의 세션 ID를 읽고 DB 조회해서 직접 `HttpContext.User` 채우기
- 자유도는 높지만 `[Authorize]`, `AuthenticationScheme` 등 지금 얻고 있는 프레임워크 지원을 손수 재구현해야 함
- 특별한 이유가 없다면 경로 A를 우선 검토

<br>

## 데이터 모델 (세션 테이블 예시)

```
Sessions
- Id            (PK, 암호학적으로 안전한 랜덤 토큰 — 쿠키 값. 추측 불가능해야 함. Guid보다 RandomNumberGenerator 권장)
- UserId        (FK -> Users.Id)
- CreatedAt
- LastActivityAt  (sliding expiration 판단용)
- ExpiresAt
- RevokedAt     (nullable — 로그아웃/강제 로그아웃 시 시각 기록. null이면 아직 유효)
- UserAgent     (선택 — "내 로그인 기기 목록" UI, 이상 접속 감지용)
- IpAddress     (선택 — 동일 목적)
```

<br>

## 흐름별로 무엇이 바뀌는가

### 로그인
1. 세션 ID 생성 (랜덤, 추측 불가능해야 함 — 이게 곧 쿠키 값이 되므로 세션 ID가 예측 가능하면 전체가 뚫림)
2. `Sessions` 테이블에 `UserId`, `ExpiresAt` 등과 함께 insert
3. **중복 로그인 제한은 여기서 결정**: insert 전에 "이 `UserId`로 이미 활성(`RevokedAt IS NULL AND ExpiresAt > now`) 세션이 있는가" 조회
   - 정책 A (기기 1개만 허용): 있으면 기존 걸 `RevokedAt = now`로 무효화하고 새로 발급 — 새로 로그인하면 이전 기기는 자동으로 튕겨나감
   - 정책 B (다중 로그인 자체를 거부): 있으면 로그인을 막고 에러 반환
   - 정책 C (개수 제한): N개까지 허용, 넘으면 가장 오래된 세션부터 무효화
4. 쿠키에는 이 세션 ID만 `Set-Cookie`로 내려줌

### 매 요청 (인증 확인 — 지금의 `UseAuthentication()`에 해당)
1. 쿠키에서 세션 ID 추출
2. `Sessions` 테이블 조회 — 존재하는지, `RevokedAt IS NULL`인지, `ExpiresAt`이 안 지났는지
3. 통과하면 `UserId`로 `HttpContext.User` 구성 (필요 시 `LastActivityAt`/`ExpiresAt` 갱신 — 지금의 `SlidingExpiration`에 해당하는 걸 여기서 직접 구현)
4. 통과 못하면 401

### 로그아웃 (사용자 본인)
- 쿠키의 세션 ID로 해당 행 `RevokedAt = now`
- 클라이언트 쿠키도 만료 지시 (`Set-Cookie`)

### 강제 로그아웃 — **이게 지금 방식과 결정적으로 다른 지점**
- 관리자가 특정 `UserId`의 모든 활성 세션을 한 번에 `RevokedAt = now`로 업데이트
- 이미 브라우저에 남아있는 쿠키는, **다음 요청이 오는 순간** 서버가 `Sessions` 테이블 조회 → `RevokedAt` 존재 확인 → 401 처리 → 즉시 무력화
- 클라이언트의 협조(로그아웃 버튼 클릭) 없이 서버 단독으로 세션을 끊을 수 있다는 게 핵심

<br>

## 다시 상기하는 트레이드오프

| | 얻는 것 | 잃는 것 |
|---|---|---|
| 전환 후 (서버 세션) | 즉시 강제 무효화, 중복 로그인 제어, 활성 세션 목록/감사 가능 | 매 요청마다 DB(또는 Redis) 조회 필요, 서버가 무상태가 아니게 되어 다중 서버 운영 시 세션 저장소를 공유해야 함 |

단일 서버로 운영 중이라면 두 번째 단점은 크게 문제되지 않지만, 서버를 여러 대로 늘리는 시점엔 `Sessions` 테이블(또는 Redis)을 모든 서버가 공유하도록 인프라를 갖춰야 합니다.

## 지금은?

게시판 규모에서 위 트리거(강제 로그아웃/중복 로그인 제한 요구)가 실제로 생기기 전까지는 지금 구현한 Cookie Authentication(self-contained) 방식 그대로 두는 게 맞습니다. 이 문서는 그 요구가 실제로 생겼을 때 꺼내 보는 용도입니다.
